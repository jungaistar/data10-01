## 결정과 이유

- **타수는 세 가지 길로 셉니다.** 수강생 샘플 칸에 「프레스 누적 타수」와 「금형 타수」가 함께 있어, 「타수(이 행에서 친 횟수)」 열 → 같은 프레스의 누적 타수 차이 → 같은 금형의 누적 타수 차이 순서로 씁니다. 「금형 타수」는 그 행의 횟수로 읽었습니다(가정, 기획서 10장 4번). 둘 다 있으면 「누적 차이 = 그 사이 타수 합」인지 점검해 어긋난 곳을 보여 줍니다. 누적값이 줄면(카운터 초기화) 그 행은 비웁니다 — 큰 음수가 합계를 망치지 않게.
- **금형 사용 타수 = 시작 시점 사용 타수 + 사용 시작일(교체일)부터 로그 타수.** 로그가 금형의 일생 전체를 담지 않으므로 기준표에 시작값을 둡니다. 「교체 기록」 버튼이 시작일을 바꾸고 시작값을 0 으로 되돌립니다. 오버홀도 같은 구조(마지막 오버홀 뒤 로그 이전 타수)입니다.
- **예정일은 최근 14일 일평균(쉬는 날 포함 달력 일수)으로 추정합니다.** 가동일로만 나누면 실제보다 빨리 닿는 것처럼 나옵니다. 최근에 안 쓴 금형은 예정일을 내지 않습니다.
- **이상 감지는 통계 기준까지입니다(강사 결정).** 고장 이력이 없어 「무엇이 고장 신호인지」 배울 수 없으므로, 채널마다 최근 14일을 바로 앞 42일 기준선과 비교합니다.
  - 기준선은 **중앙값·MAD**(×1.4826) 가 기본입니다. 평균·표준편차는 튀는 값 몇 개에 흩어짐이 크게 잡혀 오히려 둔해집니다(테스트로 확인).
  - **기준선 구간을 최근 구간 바로 앞에 둡니다.** 매일 직전 며칠로 기준선을 다시 잡으면(순수 이동 기준선) 서서히 오르는 추세를 기준선이 따라가 놓칩니다 — 심어 둔 P2 가 바로 그 모양입니다.
  - **지속 조건**: ±3σ 를 가동일 3일 연속 넘어야 「점검 필요」. 하루 튄 값은 판정하지 않고, 연속이 아니어도 ±3σ 2일이면 「주의」. 처음 만든 판에서 하루 튄 값도 「주의」로 했더니 샘플 P2 진동이 평소와 같은데도 주의가 떠서(중앙값 −2.4%) 바꿨습니다.
  - 값이 거의 같으면(반올림된 온도 등) σ 가 0 에 가까워 아무 변화에나 경보가 납니다. 기준선의 0.5% 를 σ 바닥값으로 둡니다.
  - 모든 기준값(구간·k·연속 일수·방식·채널)은 설정에서 바꿉니다.
- **프레스 종합 상태 = 가장 나쁜 것.** 이상 감지·오버홀·최근 14일에 그 프레스에서 쓴 금형의 수명 가운데 가장 나쁜 수준을 따르고, 근거를 모두 적습니다. 카드에는 짧은 근거(평소 → 최근, 연속 일수), 이상 감지 화면에는 전체 근거를 보입니다.
- **기준일 = 로그 마지막 날.** 오늘 날짜로 하면 로그를 늦게 넣을수록 오버홀 날수만 늘고 타수는 멈춰 어긋납니다. 화면마다 기준일을 적었습니다.
- **AI 는 반자동, 이름은 가림.** 프롬프트에는 계산된 상태·근거·예정일만 넣고 로그 원본은 넣지 않습니다. 금형명에 실제 품번이 들어갈 수 있어 프레스·금형 이름을 「설비N」「금형N」 으로 바꾸고, 가린 뒤 남은 이름을 다시 찾는 안전망을 둡니다. 답을 붙여 넣으면 별칭을 되돌리되 「설비 3대」「금형2개」 같은 수 세는 말은 그대로 둡니다.
- **외부 망·협력사 접속.** 정적 페이지라 GitHub Pages 주소는 외부에서 열리지만 데이터는 브라우저마다 따로입니다. 협력사가 같은 데이터를 함께 보려면 로그인·권한·공유 DB 가 필요해 2단계(Supabase)로 두었습니다. 1단계에서는 기준표 엑셀·JSON 백업으로 주고받을 수 있게 했습니다.
- **엑셀 날짜는 일련번호로 읽습니다**(`cellDates:false`). 날짜 객체로 받으면 시간대에 따라 하루가 밀리는 경우가 있어, 일련번호를 직접 날짜·시각으로 바꿉니다.

## 결정과 이유

- **「금형 타수」를 누적 카운터로 바꿨습니다.** 받은 로그에서 0 → 719 로 오르고 교체 때 0 으로 돌아가는 값이었습니다. 1단계는 「그 행에서 친 횟수」로 가정했었습니다(기획서 10장 4번). 하루 타수 칸은 「타수」라는 이름으로 계속 읽습니다.
- **σ 기본값은 표본 표준편차.** 교과서의 개별값 관리도(I-MR)는 MR̄/1.128 을 쓰지만, 받은 로그의 앞뒤 값 상관이 전류 0.96·온도 0.99 라 이동범위가 매우 작습니다. 처음 1시간 기준으로 재 보니 이동범위 방식은 온도 3,425점·전류 2,520점이 관리선 밖, 표본 표준편차는 0점이었습니다. 두 방식 모두 고를 수 있게 하고 이유를 화면에 적었습니다.
- **추가 규칙(연속 9점 등)은 기본 끔.** 같은 까닭으로 2초 값에선 전류 3,600점 중 3,086점이 「연속 9점 한쪽」에 걸렸습니다. 1분·5분 평균으로 묶어 보는 보기를 두어, 묶은 값에서 켜 보게 했습니다(샘플 P4 전압 0.3V 내려앉음은 1분 평균에서만 또렷함).
- **2초 원값은 정상이어도 ±3σ 를 우연히 넘습니다(370점에 1점, 약 12분에 한 번).** 이어진 이탈점은 한 번(사건)으로 묶어 목록을 짧게 했습니다.
- **정지 구간 값은 관리도에서 뺌(기본).** 정지하면 전류가 공회전 값으로 떨어져 늘 LCL 밖으로 나옵니다. 정지 판정은 「앞 타수와 뒤 타수 사이가 60초(6사이클)를 넘는 구간」입니다.
- **기준 구간은 「처음 N개(1,800개 = 1시간)」가 기본, 보는 구간과 따로.** 「최근 10분」을 보더라도 관리 한계는 기준 구간에서 잡습니다(그렇지 않으면 보는 구간이 바뀔 때마다 한계가 따라 움직여 관리도가 아님).
- **큰 파일은 4MB 조각씩, 조각마다 화면에 양보.** 웹 워커는 `file://` 로 열 때 막히는 브라우저가 있어 쓰지 않았습니다. 행은 바로 타입 배열 묶음으로 쌓아 메모리를 줄였습니다(17만 행 ≈ 수 MB).
- **그래프는 600칸으로 줄이되 이탈점은 줄이지 않습니다.** 칸마다 최소~최대 세로줄 + 평균선. 이탈점이 2,000개를 넘으면 칸마다 가장 먼 점 하나만 그리고 그렇다고 적습니다.
- **2초 로그 → 하루 묶음.** 프레스·날짜·금형마다 한 행(타수 합, 정지·끊김을 뺀 가동 시간, 정지 아닌 값의 평균)으로 기존 기록에 넣어, 금형 수명·오버홀·「최근 14일 vs 앞 42일」 판정·월별 보고서가 그대로 이어집니다. 같은 날을 다시 넣으면 그 프레스의 하루 묶음을 새로 만듭니다.
- **「최근 N분」은 로그 마지막 시각 기준.** 지금은 파일을 넣을 때마다 갱신되는 구조라 「지금 시각」 기준이면 빈 화면이 됩니다.

## 결정과 이유

- **전체 구간 기준의 함정을 화면에 드러냄.** 수강생 결정대로 기본은 전체 구간입니다. 그런데 전체 구간에는 고장 직전 값도 들어가 σ 가 커집니다. 가상 데이터로 재 보니 P1 베어링 고장의 진동 경보가 전체 구간 기준 2.6시간 전, 고장 전 구간을 뺀 기준 22.4시간 전이었습니다(헛경보 후보 6 → 16번). 결정을 바꾸지 않고 「고장 전 이탈」 화면에 두 기준을 나란히 보여, 실제 데이터에서 다시 정할 수 있게 했습니다.
- **경보 = 10분 안에 ±3σ 밖 5번.** 2초 값은 정상이어도 370개에 1개꼴로 넘습니다. 한 점마다 경보하면 하루 수십 번입니다. 처음 만든 판(예열 중 이탈을 그대로 세고, 가상 모델의 「차가울 때 전류·진동이 높음」 효과도 컸던 판)은 헛경보 후보가 24번이었고, 대부분이 아침 08:00 첫 가동 무렵이었습니다. 예열 구간(온도 < 예열 끝) 이탈을 빼는 것을 기본으로 하고 모델의 그 효과를 줄이니 6번이 됐습니다. 빼기는 끌 수 있습니다.
- **온도 경계 기본값 = 안정 기준 − max(3σs, 2℃) / + max(4σs, 3℃).** 안정 기준은 기록이 30분 넘게 이어진 구간마다 뒤쪽 절반(예열이 끝난 뒤)의 중앙값입니다. σs 만으로 잡으면 온도가 아주 고르게 나와(0.2℃ 안팎) 위험선이 안정 온도 바로 위(+0.8℃)에 붙어 날마다의 차이에도 경보가 납니다 — 그래서 최소 여유(2℃·3℃)를 두었습니다. 실제 유압유 허용 온도가 있으면 그 값으로 바꾸는 것이 맞고, 화면에 그렇게 적었습니다.
- **위험 경보는 30초 넘게.** 가상 P2 에서 온도가 위험선(50℃) 근처를 몇 초씩 넘나든 것이 18번이었습니다. 30초 조건으로 실제 과열 1번만 경보합니다.
- **리드타임은 「경보가 울린 시각」부터.** 처음 벗어난 점이 아니라 경보 조건(5번째 이탈)이 찬 시각으로 셉니다 — 실제로 알 수 있었던 때가 그때라서입니다. 처음 벗어난 때도 목록에 함께 적었습니다.
- **고장 전 살펴볼 구간 = 24시간, 앞선 고장·정비 뒤부터.** 처음 48시간으로 했더니 P2 고장의 「첫 경보」가 이틀 전 우연한 전압 이탈로 잡혀 리드타임이 47.9시간으로 나왔습니다. 길게 볼수록 우연한 경보가 앞서 잡힙니다. 바꿀 수 있습니다.
- **실시간 관리선은 고정.** 받은 값으로 계속 다시 잡으면 고장 징후를 따라 선이 올라가 경보가 늦어집니다(시험에서 온도 넘침을 넣은 뒤 잡은 위험선이 69℃ 로 따라 올라감). 그 프레스의 가져온 2초 로그가 있으면 그것으로, 없으면 받기 시작한 처음 10분(300개)으로 잡아 고정합니다.
- **브라우저는 설비와 직접 말할 수 없음.** Modbus TCP·OPC UA 는 브라우저가 열 수 없는 연결이라, 페이지는 HTTP·WebSocket 만 받고 그 앞에 게이트웨이·중계를 둡니다(기획서 12.4). 중계 견본은 의존성 없이 Node 하나로 돌게 했고, 같은 서버가 페이지도 내놓아 같은 출처로 열 수 있게 했습니다(공개 HTTPS 페이지 → 내 PC http 는 브라우저마다 다르게 막힘).
- **밖으로 나가는 것은 그 요청뿐.** HTTP 받기는 GET 만, `credentials: 'omit'`, 본문 없음. 받은 값은 메모리에 두고 「2초 로그에 합치기」를 누를 때만 IndexedDB 에 저장합니다. 시뮬레이터는 요청이 없습니다.
- **판 섞임 막기.** data10-11 에서 학생 브라우저가 옛 js 와 새 js 를 섞어 돌린 일이 있어, 모든 css·js 에 `?v=` 판 질의를 붙이고 fresh-guard v3 를 넣었습니다. file:// 로 열면 fresh-guard 의 HEAD 요청을 브라우저가 거절하며 콘솔에 한 줄 남깁니다(동작에는 영향 없음, 정본 그대로 둠 — 브라우저 점검에서 이 한 줄만 셈에서 뺌).

## 결정과 이유

- **저장 자료는 지우지 않습니다.** 옛 금형 · 오버홀 기준표(db.dies, db.presses 의 주기 칸)와 판정 기준의 수명 · 주기 값은 저장된 채로 두고 읽기만 하지 않습니다. 설정에서 종류 · 메모를 저장해도 옛 칸을 덮지 않게 합쳐서 저장합니다. 옛 주소 `#/die` 등은 대시보드로 갑니다.
- **라벨 규칙**: 설비가 같고 [발견 일시 − 고장 전 구간, 조치 일시] = 이상(양 끝 포함), (조치 일시, 조치 + 안정 구간] = 제외, 나머지 정상. 고장 전 구간 기본 24시간은 「고장 전 이탈」의 lookbackH 24 와 같은 정의로 맞췄습니다(시험으로 P2 구간 시작이 같은지 확인). 두 이력이 겹치면 이상이 제외보다, 수동 라벨이 규칙보다, 나중 수동이 먼저 수동보다 앞섭니다.
- **설비 이름 대조**는 띄어쓰기 · 대소문자 · 「-」 「_」만 무시합니다(PRESS-03 = press03). P3 와 PRESS-03 처럼 다른 이름은 맞추지 않고 표에 「설비 이름 확인」으로 알립니다 — 지어서 맞추면 틀린 라벨이 붙습니다.
